# CLAUDE.md

## Контекст

**Проект: «Брайер»** — веб-приложение для коллективного прогнозирования
событий с оценкой точности прогнозов. Репозиторий: `brier-term-paper`.


Курсовой проект по веб-разработке. Автор — Эмиль, студент техникума,
уровень начинающий. Проект защищается устно: преподаватель спрашивает
про общую структуру и про конкретные места в коде.

**Код должен быть таким, чтобы автор мог объяснить любой его фрагмент.
Понятность важнее элегантности, краткости и производительности.**

## Главный критерий

Перед написанием любого кода проверь:

> Объяснит ли это студент второго курса за 30 секунд, не открывая документацию?

Нет — переписывай проще. Этот критерий важнее DRY, расширяемости
и «правильных практик».

Если простое решение объективно плохое (дыра в безопасности, всё ломается
на 20 записях) — скажи прямо, объясни trade-off, предложи выбор.
Не подсовывай сложное решение молча.

## Ограничения по коду

Запрещено без явного разрешения:

- наследование глубже одного уровня, абстрактные классы, интерфейсы, mixins
- паттерны: Factory, Strategy, Repository, Observer, DI, Service Layer
- свои декораторы, метаклассы, магические методы кроме `__init__` и `__str__`
- `async`/`await`, многопоточность, очереди задач
- вложенные comprehension, тернарник в тернарнике, сложные лямбды
- регулярки без построчного комментария
- абстракции «на будущее»: конфиг-слои, плагины, обобщённые обработчики
- библиотеки, которые не обсуждались отдельно

Обязательно:

- явные имена: `get_user_by_email`, не `fetch` / `handle` / `process`
- одна функция — одна задача, до ~30 строк
- файл до ~200 строк; больше — предложи разделение и объясни по какому признаку
- вложенность до 3 уровней, ранний `return` вместо длинных `else`
- `try/except` вокруг конкретной операции, не глобальный перехватчик
- комментарий там, где неочевидно **почему**, а не «что делает строка»

Классы допустимы там, где их требует фреймворк: модели, формы,
представления. Всё остальное — обычные функции.

## Порядок работы

1. **План до кода.** Какие файлы затрагиваются, какие функции появятся,
   что каждая делает одним предложением, как связано с существующим.
   Ждёшь подтверждения.
2. **Маленькие куски.** Максимум 2–3 файла за шаг, одна логическая единица
   («форма регистрации», не «модуль пользователей»).
3. **После кода — запусти skill `explain-step`.** Без исключений.

## Стиль общения

- по-русски; термины, библиотеки и код — на английском
- новый термин объясняется при первом появлении, одной строкой
- сначала вывод, потом обоснование
- без «как вы знаете» и «очевидно»
- не соглашайся из вежливости: неудачный план — скажи и объясни

## Чего не делать

- не рефакторить рабочий код без запроса — автор в нём уже разобрался
- не добавлять функциональность, о которой не просили
- не оптимизировать: нагрузка учебная
- при двух возможных прочтениях задачи — спрашивай, не угадывай
- не выдумывать версии библиотек, названия методов, параметры API

## Стек

Утверждён 2026-09-04. Новые зависимости — только после обсуждения.

- Backend: Python 3.12, Django 5.x, Django REST Framework
- База данных: PostgreSQL 16
- Frontend: React 18 + Vite, чистый JavaScript (без TypeScript)
- Маршрутизация: React Router
- Стили: Tailwind CSS v4 через плагин Vite
- Графики: Chart.js через react-chartjs-2
- ML: scikit-learn, pandas, joblib
- Сервер: VPS Ubuntu, nginx + gunicorn + systemd, HTTPS через Let's Encrypt

### Правила для backend

- представления только функциональные, никаких class-based views
- аутентификация — встроенные сессии Django, не JWT
- фронтенд отдаётся с того же домена, поэтому CORS не используется
- админка остаётся серверной, на шаблонах Django, по адресу /admin/

### Правила для frontend

- из хуков только useState и useEffect
- никаких Redux, Zustand, React Query и прочих менеджеров состояния
- запросы к API — обычный fetch внутри useEffect
- никаких UI-библиотек (MUI, shadcn, Ant Design): стили только через Tailwind
- один компонент — одна страница или один заметный блок, файл до ~150 строк
